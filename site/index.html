3 · Test design

How the test cases were derived

saucedemo has no written rules for names or zip codes, so these are characterization tests: they record what the site does today (it accepts all input) instead of guessing a rule. Whether a real shop should reject some of that input is a product question, not a test question.

4 · Findings

Two known defects

Both are low severity on a demo site, but they would matter in a real shop. Each one has a test that checks the correct behaviour and is marked test.fail until the site is fixed.

An order can be placed with an empty cart

Low severity · R1
  1. Log in and open the empty cart.
  2. Check out and fill in the form.
  3. The overview shows a total of $0.00 and Finish still works.

Test: an empty cart cannot be ordered

Browser Back after finishing allows a second order

Low severity · R4
  1. Complete an order.
  2. Press the browser Back button.
  3. The overview reappears; Finish confirms a second order.

The cart was already emptied by the first order, so the second one is also an empty order. Test: browser Back cannot place a second order

5 · Reading the report

Why two ✘ still mean a green run

test.fail tells Playwright that a test is expected to fail. The two known-defect tests check the correct behaviour, so they fail while the defect exists, and Playwright counts that as a pass. They take about 5 seconds each, because they check that something does not happen and wait the full timeout.

Defect still there
Test checks the correct behaviour
Assertion fails, shown with ✘
Counted as passed · CI stays green
Defect fixed
Test checks the correct behaviour
Assertion passes
“Expected to fail, but passed” · remove test.fail

A ✘ on any other test is a real failure: the summary shows failed and CI turns red.

7 · Automation

CI and publishing

GitHub Actions runs the suite on every pull request and every push to main, in the official Playwright Docker image with Chromium preinstalled. On main it also publishes this page and the report to Vercel, even when tests fail.

Credentials

Never in the repo. Locally from .env; in CI from the secrets SAUCE_USERNAME and SAUCE_PASSWORD. A missing one stops the run with a clear message.

Reliability

Two retries in CI, a single worker, and forbidOnly so a stray test.only cannot slip through. Traces are recorded on the first retry.

Upgrades

When @playwright/test is upgraded, the Docker image tag in the workflow moves to the same version.

8 · Honest boundaries

Limitations

  • Chromium only; Firefox and WebKit are not tested.
  • The tests depend on the live saucedemo.com site being up. There is no local copy.
  • Three tests submit the same valid customer. They stay separate because each covers a different risk.
  • Neither CI nor npm test checks TypeScript types; Playwright runs the tests without type checking.
Published by CI after every push to main. Full documentation is in the repository README. Screenshots: saucedemo.com, a public demo shop by Sauce Labs.
